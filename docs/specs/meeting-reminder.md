# Meeting Reminder

## Goal

Surface the user's Google Calendar meetings for today directly in the Kool Kits toolbar action, so an imminent meeting is visible at a glance (a red badge) and one click reveals what is in progress, what is coming up next, and how to join.

## Connection

The extension reads the user's calendar by reusing the Google session they are already signed into in the browser. It calls the same internal endpoint the Google Calendar web app uses to load events, authenticated by the browser's existing Google cookies rather than by an OAuth token the extension holds. This was chosen over Chrome's identity flow (`chrome.identity.getAuthToken`) because that flow requires an OAuth client registered in Google Cloud against the extension ID, and the target organization blocks both new Google Cloud project creation and the personal "secret iCal address" egress path — leaving no usable way to provision an OAuth client for a personal-productivity extension. Reusing the browser session sidesteps OAuth entirely: there is no client ID to register, no consent screen, and no token to refresh or revoke.

There is therefore no "authorization" the extension owns and no token lifecycle. The extension tracks a single **connection status** in its meeting cache: whether it is actively using a calendar account (`CONNECTED`, with that account's email), deliberately disconnected by the user (`DISCONNECTED`), unable to find a Google session on sync (`SESSION_UNAVAILABLE`), or still linked to an account but blocked by a failed bootstrap or events fetch (`BOOTSTRAP_FAILED` or `EVENTS_SYNC_FAILED`). Signed-out and expired browser sessions surface as `SESSION_UNAVAILABLE`; a user-initiated disconnect surfaces as `DISCONNECTED` and does not auto-reconnect while Google may still be signed in. Older caches that stored a legacy `disabled` sync state from the feature toggle are upgraded to a non-disconnected status when the user had not explicitly disconnected; only `disconnectedByUser` forces `DISCONNECTED` on upgrade.

The connected account is whichever Google account is the browser's primary session (account index `u/0`). The account's email is read from the same authenticated page load that the events come from, so the email and the session can never drift apart: they originate from one request. The events request and the account-identification request are pinned to the same account index so they always describe the same account. Reading a different account, account pickers, and non-Google providers are intentionally deferred.

Connecting is therefore not a credential prompt but a guided flow: when the status calls for the connect screen (`DISCONNECTED` or `SESSION_UNAVAILABLE`), the user starts connect from the popup or options page. The UI shows a **Connecting…** state immediately while the service worker runs a background sync first so an existing Google session can promote to `CONNECTED` without opening Calendar. If sign-in is still required, the worker reuses an open Google Calendar tab when one exists (focuses it and reloads to the primary account view) or opens Calendar in the foreground when none exists. The options page listens for connection cache and pending-connect storage changes so the row updates as soon as sync finishes without a manual refresh. After a connect that needed the Calendar page, a short success toast on that tab tells the user they can close it. A successful connect path promotes the status to `CONNECTED` and loads meetings. The extension holds no OAuth grant to revoke. Ending Google access in the browser moves the status to `SESSION_UNAVAILABLE` on a later sync. Separately, when the extension shows `CONNECTED`, the user can **disconnect** in options: that sets `DISCONNECTED`, wipes cached meetings and the connected email, clears the badge, and stops calendar syncing until the user connects again. Disconnect does not sign the user out of Google.

Because the session can expire at any time, a previously `CONNECTED` extension can move to `SESSION_UNAVAILABLE` on the next sync while keeping the last cached meetings for the badge and popup. The user must always be able to tell whether the extension is connected and as which account. Whether the Meeting Reminder feature itself is on or off is a separate setting and does not live in the connection status.

## Data Model And Sync

The service worker owns all calendar data and badge state so the badge stays trustworthy even while the popup is closed. This is the only architecture that keeps the reminder badge correct without depending on the user opening the popup.

When the feature is disabled (see Options), the service worker performs no routine calendar syncing and keeps the badge cleared. A user-initiated connect while the feature is off still runs connection detection only (no events fetch) and can promote the status to `CONNECTED` with the detected account email; re-enabling the feature afterward resumes normal syncing and event fetch without requiring another connect.

While enabled, the service worker fetches today's events on a periodic schedule, normalizes them, and caches them in extension storage together with a last-synced timestamp, the connected account's email when known, and the connection status. Each sync runs in two phases: connection detection (session/bootstrap) then, only when a session account is identified, today's events fetch. If no account can be identified, connection detection sets `SESSION_UNAVAILABLE` without clearing cached meetings. When an account is identified, the events phase fetches that account's calendar for today and sets `CONNECTED`. It also refetches when the popup opens, so the user sees fresh data when they look. While the status is `DISCONNECTED`, background sync does not promote back to `CONNECTED` until the user uses the connect action (opening Google Calendar from the extension). Reconnect intent is persisted in extension storage so a service-worker restart between opening Calendar and the next sync does not drop the pending connect. That pending reconnect is cleared only after a successful `CONNECTED` sync, so a sign-in flow that first lands on Calendar before the Google session is usable can retry on the next Calendar load even when the feature is off. An in-flight sync that started before a user disconnect cannot overwrite the disconnected cache: the worker bumps a sync generation on disconnect and ignores stale sync cache writes and badge refreshes.

A transient fetch failure (offline, server error) is not destructive: the last good set of cached meetings is retained and continues to drive both the badge and the popup, and the status becomes `BOOTSTRAP_FAILED` or `EVENTS_SYNC_FAILED` depending on which step failed. This is essential to the badge's core promise — a single failed background fetch must not make an imminent meeting's badge disappear or blank the popup's cached list. Cached meetings are cleared on user disconnect, not when the feature toggle is turned off (the toggle only stops syncing and clears the badge). `SESSION_UNAVAILABLE` and the fetch-failure statuses preserve the last cached meetings so a brief lapse does not blank the popup.

Calendar syncs are coalesced into a single in-flight operation. Multiple triggers (the periodic alarm, a popup-open refresh, a Calendar tab load, and a settings change) can fire close together; without coalescing, a slow failing sync could overwrite the result of a newer successful one. Overlapping triggers therefore share one in-flight sync rather than racing on the cache, and any trigger that arrives while a sync is active schedules one immediate follow-up sync so a Calendar load that happens during an older request is not swallowed until the next alarm.

Only events that represent real, time-bound commitments are kept: all-day events are excluded because they have no specific start to remind on, and non-meeting calendar entries (working-location, focus-time, and out-of-office blocks) are excluded because they are not meetings to join or be reminded of. Which response statuses are kept is user-configurable (see Options): the default keeps everything except meetings the user has explicitly declined, while the alternative keeps every event regardless of response. In both modes all-day events are still excluded. Events the user has not responded to (no RSVP yet) are treated like tentative and kept in the default mode — only an explicit decline removes a meeting in the default mode. Only the primary calendar is consulted. This is a deliberate, known limitation: meetings that live only on a shared, team, or other secondary calendar will not appear or drive the badge. A calendar picker was considered and deferred to keep the first version simple; adding one later means letting the user select calendars and fetching and merging events per selected calendar.

A separate recompute step updates the toolbar badge from the cached events without making network calls, so the badge reflects the passage of time (counting down, flipping to in-progress, clearing when meetings end) between data fetches. The service worker schedules a one-shot alarm for the next moment badge or popup grouping can change (meeting start or end, entering the lead window, or the next whole-minute countdown step) because Chrome's periodic alarm API cannot repeat below one minute. The displayed countdown still rounds up to whole minutes. While the popup is open, it re-fetches grouped state from the worker on that same cache-driven schedule and on a short interval so countdown copy and list membership stay aligned with the badge. Likewise, a meeting that starts in the first minutes after midnight may not appear until the next periodic fetch picks up the new day, leaving a short blind window just after midnight.

## Badge Behavior

When the feature is disabled, there is never a badge. Otherwise the badge communicates urgency of the single most urgent meeting:

- When no meeting is within the configured lead window and none is in progress, there is no badge.
- When a meeting will start within the configured lead time, the badge shows the whole number of minutes until it starts with an `m` suffix (for example `3m`), counting down, on a red background.
- When a meeting is in progress and nothing upcoming is within the lead window, the badge shows `now` on a red background.

When meetings are concurrent or back-to-back, the soonest upcoming start within the lead window wins the badge, because the action the user most needs to take is joining the meeting that is about to begin. An in-progress meeting only drives the badge when there is nothing imminent to start.

The badge text is deliberately short because Chrome only renders a few characters. The exact lead time is user-configurable (see Options).

## Popup

The popup is structured as a header strip, a scrollable meeting section, and a footer. The header and footer are stable anchors; only the meeting section grows and scrolls, so navigation and identity stay in predictable places however long the list gets.

The header strip carries identity and connection status: the Kool Kits mark and name, and the known account email beside a status indicator (a green dot when the status is `CONNECTED`, a muted dot when no account identity is known). When the status is `BOOTSTRAP_FAILED` or `EVENTS_SYNC_FAILED` but a connected email remains cached, the header still shows that email so the user can tell whose meetings they are seeing. Surfacing the account in the popup — not only on the options page — answers "whose calendar am I looking at?" at the moment the user is reading the list, which matters because the badge and list are only trustworthy if the user can confirm the source. The header is hidden entirely when the feature is disabled, since there is then no calendar access to describe.

The meeting section is scoped to **today in the user's local timezone** but shows only what matters for a glance: meetings **in progress** ("Now") and the **next** upcoming slot ("Up next") among those still on today's calendar. A meeting stays listed until its end time has passed, then it drops out; meetings on future local days never appear, even if the sync cache still holds them or the fetch range included them. Each meeting shows its title and its start and end times in the user's locale format.

When more than one meeting is active at the same moment, every overlapping in-progress meeting appears under "Now" (two meetings cannot be in progress at the same instant without overlapping). When more than one meeting shares the same next start time, every meeting in that slot appears under "Up next"; later meetings today stay in the cache for the badge but are not listed until they become the next slot or move into "Now". The section may scroll when several meetings share a slot, but it does not enumerate the full remainder of the day.

The two groups are weighted differently because the user's glance has a priority order. An in-progress meeting is rendered as an emphasized card carrying the urgency color, a countdown to its end ("ends in 8m"), and a progress bar showing how much of it has elapsed; its primary action reads **Join meeting**. Upcoming meetings are rendered as a compact rail, each leading with the time until it starts (the soonest one within the configured lead window emphasized in the urgency color, matching the badge's logic) alongside its start and end times, with a compact **Join** action. A meeting shows a Join action only when a join link can be resolved for it; meetings without one show none. Activating Join opens the resolved URL in a new browser tab, which works uniformly whether the link is Google Meet, Zoom, Microsoft Teams, or another provider.

The displayed countdowns advance while the popup stays open: the worker re-groups cached meetings for the current time whenever the cache changes or a display transition fires, and the popup also polls on a short interval so progress bars and sub-minute copy stay smooth without another calendar fetch.

The non-list states (empty, not-connected, fetch-error) are designed screens rather than bare lines of text: each pairs an icon with a short title and a supporting line, and the not-connected screen carries the open-Google-Calendar action. The empty state confirms the user is all clear for the day rather than implying something failed.

The footer sits outside the meeting section and contains a Settings control that opens the extension's options page.

Both the popup and the options page use a dark theme by default, reusing the existing Kool Kits palette and typography established by the recent tab switcher (a dark panel background, off-white text, and the yellow accent, with `color-scheme: dark`). Color carries meaning rather than decoration: yellow marks primary actions (Join, Connect, the enabled toggle) and brand identity, red is reserved for meeting urgency (the badge, the in-progress emphasis, and an upcoming meeting once it falls inside the lead window), and a distinct green denotes a live connected Google session. Every state-bearing color is paired with text (a status word, a countdown, a label) so meaning never rests on hue alone.

Inter is bundled with the extension and loaded with `@font-face` from the package rather than relying on Inter being installed on the user's machine or fetched from a web-font CDN. Self-hosting was chosen deliberately: a CDN font would add a network request every time the popup opens, break offline, and create third-party egress from a financial-services browser, while merely naming Inter in the font stack (the prior behavior) silently fell back to a system font on most machines, so the intended typography never actually rendered. Keeping these surfaces on the same palette and type makes the feature feel native to the extension rather than introducing a second visual language.

The popup renders one of several states:

- **Disabled:** when the feature is turned off in options, the popup omits the meeting section entirely and shows only the footer with the Settings control.
- **Not connected:** a primary action that opens Google Calendar in a new tab so the user can sign in, with a brief line explaining that the extension reads meetings from the signed-in Google session. It is an instruction to sign in elsewhere, not a login form or a consent button. User `DISCONNECTED` always shows this screen. `SESSION_UNAVAILABLE` shows it only when there are no cached meetings to fall back on; otherwise the popup keeps showing the cached list like a transient fetch failure.
- **Loading:** shown only when there is no cached data yet, so a returning user with cached meetings never sees a spinner.
- **Empty:** when connected with no qualifying meetings remaining today, the section shows an empty state reading `No meeting`.
- **List:** the in-progress and upcoming groups described above. Whenever cached meetings exist they are shown, even if the most recent fetch failed transiently, so a popup opened while briefly offline keeps showing the last known meetings rather than collapsing to an error. A dedicated fetch-error message is shown only when the fetch failed and there are no cached meetings to fall back on.

## Join Link Resolution

A meeting's join link (the "video call" link, named for the user-facing Join action — not video content) is resolved in priority order: first a direct provider link when present, then a video entry point from the event's structured conferencing data, then a scan of the event description and location for recognizable meeting URLs (Google Meet, Zoom, Microsoft Teams). The first match wins. If nothing matches, the meeting has no Join button. Structured conferencing data is preferred over text scanning because it is unambiguous and provider-supplied, while description and location scanning is a best-effort fallback for events that only paste a link in. Non-video entry points (such as dial-in phone numbers) are never used for the Join action.

## Options

The options page opens in its own browser tab and contains a dedicated **Meeting Reminder** section so additional Kool Kits features can have their own sections later. The section contains:

- An **enable** switch that turns the whole feature on or off, rendered as a sliding toggle switch control (not a checkbox or radio). It is on by default. When off, the feature does no calendar syncing, clears the badge, and the popup omits the meeting section entirely (the footer and settings remain reachable). This lets the user keep the extension installed for other features without calendar access or a badge.
- A **lead time** control: a dropdown offering whole-minute values from 1 to 60, defaulting to 5. This determines how far before a meeting's start the badge begins counting down. A dropdown is used instead of a free-form number field to keep the value within a sensible range without validation.
- A **which meetings** control selecting whether the feature considers all meetings except those the user has explicitly declined (the default), or all events regardless of response (still excluding all-day). Not-yet-responded invites are treated like tentative and kept in the default mode; only an explicit decline hides a meeting there. This setting governs both the popup list and the badge, so a user who declines noise invites is not nagged by them while still seeing meetings they have not gotten around to answering.
- The **connection status**, including the email of the connected Google account when connected, so the user can confirm which calendar is being read. When connected, a **disconnect** action sits on the same row to the right of the status (indicator plus "Connected as" and the email). When not connected, that row shows "Not connected" on the left and the same open-Google-Calendar action as the popup on the right; while connect is in flight the row and button read **Connecting…** and the page updates automatically when sync completes. Connection status reflects whether a live Google session account can be identified, independent of whether the feature is enabled — so a user who has connected but turned the feature off still sees their connected account rather than being misled into thinking they must reconnect. Refreshing the options connection row runs live session detection so sign-out or account changes surface promptly without waiting for a background sync. When the feature is enabled, that refresh joins the same coalesced background sync as alarms and popup refresh (bootstrap plus today's events fetch) and only promotes the cache to `CONNECTED` after events sync succeeds; when the feature is disabled, it runs bootstrap detection only outside that sync and updates the known account without fetching events. Disconnect clears the extension's cached meetings, connected email, and sync state, clears the badge, and pauses syncing until reconnect. A confirmation step prevents mis-taps and states that disconnect does not sign the user out of Google. This is the supported way to drop cached connection state when it disagrees with what the user expects. Disconnect is independent of the enabled flag.

The section is presented as a single framed card under a Kool Kits header (the brand mark and name): a header band pairing the feature name with a one-line description and the master switch, the calendar controls below (each with a short hint explaining what it does), and a connection footer on one band. The footer mirrors the popup header's indicator language (a green dot with the account email when `CONNECTED`, an amber dot while connect is in flight, a muted dot during the initial connection check or when not connected, the cached account email with a muted indicator when a fetch failure still has a known account, and "Not connected" otherwise). When the feature is off, the calendar controls (lead time and which-meetings) are dimmed and disabled because they no longer apply, while the connection footer stays live. The disconnect action is a secondary outlined button on the right of the connected row so it reads as an intentional control paired with the yellow primary connect action, not bare link text or a separate data-management task. The open-Google-Calendar action uses the primary (yellow) button and only appears when not connected.

Settings persist in extension storage and are read by both the service worker (for badge timing) and the popup.

## Architecture

The feature is built in vanilla JavaScript with ES modules and message passing, matching the existing extension code.

- The service worker gains alarm-driven event fetching, frequent badge recomputation, message handling for the popup (read cached state, request refresh), and wiring of the toolbar action to a popup.
- A calendar session module owns reading the current session account from the authenticated Google Calendar page (identifying the account email and the web-client version the events endpoint expects) and fetching today's events from the web app's internal events endpoint using the browser's existing cookies. It also parses the endpoint's positional-array response into the internal meeting shape and reports the not-connected condition when no account can be identified.
- A meeting-reminder module holds the pure selection and display logic (a single view for popup groups and badge text at a moment, the next transition time for scheduling, in-progress versus upcoming grouping, and most-urgent badge rules) so it can be unit-tested without Chrome APIs.
- A join-link module holds the pure link-resolution logic.
- The popup and options page each have their own HTML, script, and styles.

Pure logic is deliberately separated from Chrome API and network calls so the time-sensitive, response-parsing, and provider-parsing behavior can be tested deterministically. In particular, the response parser and the account/version extraction are pure functions over captured response text, so they can be tested against fixtures without a live session.

Because the service worker is ephemeral, it holds no authoritative state in memory: there is no token to hold, all meeting data, the connected email, and sync state live in extension storage, and the periodic alarms (which persist across worker teardown) revive the worker to do their work. The worker serializes its sync operation behind a single in-flight promise so overlapping triggers neither duplicate network fetches nor clobber a newer result with an older one. To recover promptly from a session that was just established, the worker also watches for the user landing on or finishing a load of the Google Calendar site and triggers a sync then, so signing in to Calendar re-detects the account without waiting for the next periodic alarm.

## Permissions

The extension requests the additional capabilities needed to: schedule background alarms, reach the Google Calendar web host (to read events using the existing browser session) and observe navigation to that host (to re-detect a freshly established session). No OAuth client, scope, or identity permission is declared, because the feature does not use Chrome's identity flow. The toolbar action gains a default popup and the manifest declares an options page.

## Testing

Following the existing test style, the pure modules are unit-tested:

- The meeting-reminder module: badge states across time (no badge, countdown, `now`), most-urgent selection for concurrent and back-to-back meetings, in-progress versus upcoming grouping, and boundary conditions at start and end times.
- The join-link module: resolution for each supported provider via structured data, direct link, and text fallback, plus the no-link case.
- The calendar session module's pure parts, against captured response fixtures: normalizing the positional-array response into meetings (title, start, end, video link), excluding all-day and declined events, extracting the account email and web-client version from a captured page, and detecting the not-connected condition (no identifiable account).

## Acceptance Criteria

- The popup and options page render in the Kool Kits dark theme by default, consistent with the recent tab switcher's palette and typography.
- A connected user sees in-progress meetings plus the next upcoming start slot in the popup (all meetings that share that start time when concurrent), grouped into "Now" and "Up next" with clear visual separation.
- A meeting remains listed until its end time passes, then disappears.
- Each meeting shows start and end times in the user's locale; only meetings with a resolvable video link show a Join button, and Join opens that link in a new tab.
- The badge is absent until a meeting is within the configured lead time, then shows a red countdown, then `now` while a meeting is in progress with nothing imminent, then clears.
- For concurrent or back-to-back meetings, the badge reflects the soonest upcoming start within the lead window.
- The badge stays correct over time without the popup being opened.
- All-day events never appear and never drive the badge. By default, only explicitly declined events are also excluded (not-yet-responded and tentative are kept); switching the "which meetings" setting to all events includes declined ones too (all-day still excluded).
- A user who is not connected (never signed in, or session expired/signed out) sees a single connect action that shows **Connecting…**, tries a background sync first, then opens or focuses Google Calendar only when sign-in is still needed; once signed in, the extension re-detects the session, updates the options row without a manual refresh, and shows meetings without further interaction. A connected user with nothing today sees `No meeting`.
- The options page has a Meeting Reminder section with an enable switch (on by default), a 1–60 minute lead-time dropdown (default 5), a "which meetings" control (accepted/tentative by default, or all events), a connection row that shows the connected account's email with disconnect on the right when connected (or "Not connected" with open-Google-Calendar on the right when not), and disconnect sets the connection status to `DISCONNECTED` and pauses syncing until reconnect without signing out of Google. Settings changes take effect for the popup list and badge timing.
- Turning the feature off clears the badge, stops calendar syncing, and removes the meeting section from the popup while leaving the footer and settings reachable; turning it back on resumes syncing and the badge.

## Out Of Scope

- Desktop or system notifications beyond the toolbar badge.
- Multiple calendars, account pickers, and non-Google providers.
- Editing, creating, or responding to events.
- Syncing settings across devices.
- Supporting non-Chrome browsers.
